# SINE AI Expert Panel

## Overview

The **SINE AI Expert Panel** is the second layer of the SINE Incubation Intelligence Platform's startup-review workflow. It takes a completed core evaluation (Layer 1) and adds four independent specialist reviews before a human committee is involved.

Each specialist receives the startup application, selected Layer 1 findings, and the overall Layer 1 score. The specialists then assess the same startup from four distinct perspectives:

| Specialist | Focus |
| --- | --- |
| **SME** | Technical due diligence: technology authenticity, scientific validity, novelty, technical risk, and evidence required. |
| **Financial** | Revenue plausibility, unit economics, valuation, burn/runway, and scalability of the business model. |
| **Legal** | IP ownership, patentability, IIT Bombay policy considerations, regulations, incorporation, and founder agreements. |
| **Network** | SINE-specific value, alumni and investor relevance, partnerships, cohort fit, and incubation-stage suitability. |

The four agents are launched **in parallel**, rather than one after another. This keeps the panel fast while preserving separate domain opinions. Each agent returns structured JSON with a score, verdict, headline, red flags, questions for the founders, confidence, and specialist-specific findings.

This panel is an AI-assisted due-diligence tool. It provides structured review material for people to assess; it does not replace legal, financial, technical, or investment advice from qualified humans.

## System Requirements

### Runtime and services

| Requirement | Purpose |
| --- | --- |
| Node.js 24+ | Runs the TypeScript API service and supports the runtime APIs used by the application. |
| TypeScript | Provides the API types for evaluation inputs, Layer 1 scores, panel status, and expert responses. |
| Express-compatible API server | Hosts the trigger, status, and Server-Sent Events (SSE) routes. |
| Anthropic-compatible AI client | Sends one request to the selected AI model for each expert role. |
| Access to an Anthropic model | The current implementation uses `claude-sonnet-4-6`. |
| Secure environment-secret configuration | Keeps the AI integration credentials outside source code. Never place API keys in this document, a prompt, or client-side code. |
| In-memory or persistent evaluation store | Holds the application, Layer 1 scores, panel status, and completed expert results. |

### Required data from Layer 1

The Expert Panel can only start after Layer 1 is in either the `complete` or `approved` state. The evaluation record must provide:

```json
{
  "company_name": "Example Startup",
  "sector": "HealthTech",
  "stage": "Prototype/MVP",
  "problem": "The customer problem being solved.",
  "solution": "The proposed product, technology, and business approach.",
  "founders": "Founder names and relevant backgrounds.",
  "iitb_connection": "Relevant IIT Bombay relationship or context.",
  "team_size": 4,
  "revenue": "Optional revenue information",
  "customers": "Optional customer or pilot information",
  "website": "Optional website URL"
}
```

It also needs:

- The Layer 1 module scores and their written analyses.
- The Layer 1 overall score, when available.
- A unique evaluation ID used to trigger and retrieve the panel.

### Operational considerations

- **SSE is recommended for the user interface.** It lets the frontend show each specialist result as it becomes available.
- **The current store is in memory.** Restarting the API server clears ad-hoc data and restarts with its seed data. For a production deployment, replace this with durable storage.
- **Responses must contain valid JSON.** The implementation asks each model to return only one raw JSON object. If a model returns malformed content, that specialist is recorded as a manual-review fallback instead of failing the other specialists.
- **Do not expose the AI integration to browsers.** The browser should call the application API; only the server should communicate with the model provider.

## Operational Protocol (How It Works)

### 1. Complete the core evaluation

Layer 1 evaluates the startup and writes its module scores, written findings, overall score, and decision to the evaluation record. The Expert Panel refuses to run if Layer 1 is still pending or processing.

### 2. Trigger the Expert Panel

Send a request using the completed evaluation ID:

```http
POST /api/evaluate/expert-panel/{evaluationId}
```

Successful trigger response:

```json
{
  "message": "Expert panel started",
  "evalId": "evaluation-id"
}
```

The request returns immediately. The specialist analysis continues asynchronously on the server.

### 3. Validate the request before work begins

The API returns clear errors for common invalid states:

| Situation | HTTP status | Example message |
| --- | ---: | --- |
| The evaluation ID does not exist | 404 | `Evaluation not found` |
| Layer 1 is not `complete` or `approved` | 400 | `Layer 1 evaluation must be complete before running expert panel` |
| A panel is already running for the evaluation | 409 | `Expert panel is already running` |

When accepted, the panel status becomes `running` and previous panel results for that evaluation are cleared.

### 4. Build specialist context

Every specialist receives the startup's identity, sector, stage, team, problem, solution, IIT Bombay connection, and the Layer 1 context relevant to that specialist. For example:

- The **SME** receives technical, differentiation, and market findings.
- The **Financial** specialist receives business-model, traction, and market findings.
- The **Legal** specialist receives defensibility, technology, and SINE-fit findings.
- The **Network** specialist receives SINE-fit, team, and market findings.

The prompt asks each specialist for a strict raw JSON object, not prose or Markdown.

### 5. Run all four specialists concurrently

The server launches SME, Financial, Legal, and Network requests at the same time using a parallel wait. A slow legal review does not delay the start of the other three reviews.

As each specialist finishes:

1. Its response is parsed into a structured expert result.
2. The result is added to the evaluation's in-progress results.
3. The panel status record is updated.
4. Connected SSE clients receive a progress event.

While the panel is still running, results can arrive in **completion order**. Once every request resolves, the final completed result set is stored in the configured specialist order: SME, Financial, Legal, Network.

### 6. Stream progress (optional but recommended)

Connect the frontend to:

```http
GET /api/stream/expert-panel/{evaluationId}
```

The endpoint emits Server-Sent Events approximately every 600 ms when a new specialist result is available.

Example progress event:

```text
event: progress
data: {
  "message": "SME complete — 6.8/10",
  "agentIndex": 0,
  "totalAgents": 4,
  "currentAgent": "Financial",
  "result": { "...specialist result..." },
  "allResults": [{ "...first result..." }],
  "panelStatus": "running"
}
```

When all specialists are complete, the stream sends:

```text
event: complete
data: {
  "message": "Expert panel complete",
  "allResults": [{ "...four specialist results..." }],
  "panelStatus": "complete"
}
```

### 7. Retrieve the current or completed result

Use the status endpoint whenever a client reconnects or does not use SSE:

```http
GET /api/evaluate/expert-panel/{evaluationId}
```

Possible `status` values are:

| Status | Meaning |
| --- | --- |
| `not_started` | No panel has been launched for this evaluation. |
| `running` | One or more specialists are still working. Partial results may already be available. |
| `complete` | All four specialist results have been collected. |
| `error` | An unexpected panel-level failure prevented completion. |

### 8. Handle failures safely

Each specialist request has its own error boundary:

- If one specialist fails or returns content that cannot be parsed as JSON, it receives a fallback result.
- The fallback has score `5.0`, verdict `Discuss`, confidence `low`, a `manual review required` headline, and an `Automated agent failed` red flag.
- The other specialists continue and the panel can still complete normally.

Only an unexpected failure outside these per-specialist safeguards sets the whole panel to `error` and sends an SSE `error_event`.

### 9. Consume the result responsibly

Present the four specialist views alongside the Layer 1 evaluation. Use low-confidence fallback output as a clear signal to request a human review or rerun the affected specialist. A downstream committee workflow can use the completed panel as input, but committee matching and final admission decisions are separate processes.

### Shared result fields

Every specialist result includes these fields:

| Field | Type | Meaning |
| --- | --- | --- |
| `agent` | string | One of `SME`, `Financial`, `Legal`, or `Network`. |
| `score` | number | Specialist assessment on a 1–10 scale. |
| `verdict` | string | Specialist recommendation, such as `Approve` or `Discuss`. |
| `headline` | string | One-sentence summary of the specialist view. |
| `red_flags` | string[] | Specific risks that require attention. |
| `what_ai_missed` | string[] | Nuances that the Layer 1 review may not have covered. |
| `questions_for_founders` | string[] | Follow-up questions for the founding team. |
| `confidence` | string | The specialist's confidence level, such as `low`, `medium`, or `high`. |

Specialists may also return extra domain-specific fields, as shown in the sample. Consumers should preserve these fields rather than discard them.

### Fallback result for a failed specialist

```json
{
  "agent": "Legal",
  "score": 5,
  "verdict": "Discuss",
  "headline": "Agent could not complete — manual review required.",
  "red_flags": [
    "Automated agent failed"
  ],
```

## Adoption Checklist for Another Repl

1. Add an AI provider integration and configure its credential as a server-side secret.
2. Store the startup input, Layer 1 score objects, panel status, and results.
3. Implement the trigger, results, and optional SSE endpoints with the protocol above.
4. Create four role-specific prompts that require a raw JSON object.
5. Launch all four AI calls concurrently and isolate failures per specialist.
6. Display partial results while the panel runs and mark fallback results as requiring human review.
7. Replace in-memory storage with a durable data store before using the workflow in production.
